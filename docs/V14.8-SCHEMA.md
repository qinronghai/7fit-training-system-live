# V14.8 Data Schema

## Status

V14.8 introduces the first versioned data-contract layer for the 7Fit Training System runtime dataset.

Issue #3 established the Schema contract without changing training semantics. Issue #4 then moved the maintenance source into domain JSON files under `data/src/`, while preserving `data/system-data.js` as the generated browser runtime bundle and keeping the same `window.V14_DATA` contract.

See also: `docs/V14.8-DATA-SOURCES.md`.

## Schema dialect and location

- Dialect: JSON Schema Draft 2020-12
- Versioned directory: `schemas/v14.8/`
- Validator: `tools/validate_v148_schema.py`
- Tests: `tests/test_v148_schema.py`

The browser does not load Python or `jsonschema`. Validation is a repository/CI concern only.

## Schema ownership

| Schema | Owns |
| --- | --- |
| `action.schema.json` | Action identity, name, route, status, tier and stable typed fields |
| `session.schema.json` | F111 session slot container and formal runtime slot-key shape |
| `composer.schema.json` | 5 lower modes, 4 upper modes, L1-L4 maps, 6 Core Demand machine keys, auxiliary rules and 8 official preset pairs |
| `support.schema.json` | SUPPORT inventory container and minimum detail contract |
| `core.schema.json` | CORE inventory container and minimum detail contract |
| `prep.schema.json` | PREP inventory, details and fixed movement-pattern match keys |
| `foam.schema.json` | Foam inventory, details and fixed movement-pattern match keys |

Schemas intentionally allow historical optional metadata unless a field has become a stable product contract. This keeps V14.8 strict on invariants without freezing incidental legacy fields prematurely.

## Frozen V14.8 runtime contract

The validator currently preserves these formal inventories:

- 32 F111 Sessions
- 8 Recipe Families
- 30 SUPPORT nodes
- 20 CORE nodes
- 20 PREP nodes
- 12 Foam nodes

Composer cardinality is also frozen exactly at:

- 5 lower modes
- 4 upper modes
- 20 legal free combinations derived from 5 × 4
- 8 official presets, `F111-01` through `F111-08`
- exactly `L1`–`L4` in the Composer level/support/core maps

Formal F111 strength slots preserve the venue rule that main selections may use `1F_ONLY` or `FLEX_1F_2F`, while the Issue #5 auxiliary policy requires D1/D2 candidates to remain `1F_ONLY`.

Routes such as `POST_CARDIO_ONLY`, `CONDITIONING_2F`, and `RECOVERY_2F` cannot become formal F111 strength-slot baselines.

When an Action carries an explicit tier, V14.8 recognizes the three independent tier families used by the product:

- Main: `T1`–`T4`
- SUPPORT: `SUP-S1`–`SUP-S6`
- CORE: `CORE-L1`–`CORE-L4`

The empty legacy tier value remains accepted where it already exists in the current runtime dataset.

PREP and Foam pattern matching are both frozen to the same eight movement-pattern keys:

- `蹲`
- `髋铰链`
- `髋伸展`
- `单腿`
- `水平推`
- `垂直推`
- `水平拉`
- `垂直拉`

Each pattern-map value must be an array of IDs because the browser runtime iterates these values as arrays. Adding a ninth match key or changing a match value into an object is a contract change and must not pass V14.8 silently.

## Important runtime-shape distinctions

### Session slot keys

The runtime stores a session-qualified key, not a short display slot name. A valid set looks like:

```text
F111-01-L1__A
F111-01-L1__B
F111-01-L1__SUPPORT
F111-01-L1__2
F111-01-L1__3
F111-01-L1__CORE
```

The validator checks both the owning Session ID and the exact suffix set `A / B / SUPPORT / 2 / 3 / CORE`.

### Core Demand

Two concepts must not be conflated:

1. `Action.coreDemand` is human-readable training-demand text, for example `抗伸展` or `基础控制 / 抗伸展`.
2. `composer.coreDemands` is the machine-key taxonomy and is restricted to:
   - `anti_extension`
   - `anti_rotation`
   - `anti_lateral_flexion`
   - `dynamic_rotation`
   - `breathing_pressure`
   - `loaded_integration`

Every Composer Core Demand entry must keep the runtime metadata shape:

```json
{
  "name": "抗伸展",
  "keywords": ["抗伸展"]
}
```

`name` must be a non-empty string and `keywords` must be a non-empty array of non-empty strings. This matches the current Composer runtime, which reads these fields when filtering and presenting Core Demand choices.

### Official preset map

Each official preset is a two-item pair:

```json
"F111-01": ["squat", "horizontal_pull"]
```

The validator checks that the first value resolves to a lower-mode key and the second value resolves to an upper-mode key. The map contains exactly the eight official preset IDs; an extra `F111-09` does not belong to the V14.8 contract.

## Validator API

`tools/validate_v148_schema.py` exposes:

```python
load_runtime_data(path: Path) -> dict
load_schema(name: str) -> dict
validate_payload(data: dict) -> list[str]
validate_repository(root: Path) -> list[str]
```

`validate_payload()` performs both JSON Schema validation and cross-record invariants that are awkward or unsafe to encode in JSON Schema alone, including references, inventory counts, Session slot ownership, Composer references, official preset references and D1/D2 route policy.

The validator intentionally reads the generated `data/system-data.js`. Issue #4's build freshness gate guarantees that this runtime bundle is exactly derived from `data/src/` before Schema validation runs.

## CLI

Run:

```bash
python tools/validate_v148_schema.py
```

Success:

```text
V14.8 schema validation: PASS
```

Failure returns a non-zero exit code and prints deterministic, path-oriented diagnostics.

## CI and release gates

Feature branches and pull requests run `.github/workflows/schema-check.yml`, which executes:

1. full Python regression;
2. `python tools/build_system_data.py --check`;
3. V14.8 schema CLI validation;
4. Node runtime tests;
5. JavaScript syntax validation.

`master` Pages deployment repeats the same build-freshness and Schema gates in `.github/workflows/deploy-pages.yml` before site artifact creation and deployment. Stale generated data or invalid formal data therefore blocks both review and release.

## Intentionally adding a new enum value or cardinality

Do not edit only `system-data.js`.

When a new formal `route`, `status`, `tier`, Composer demand key, movement-pattern key, mode, preset, or other constrained value is intentionally introduced:

1. define the product/domain reason;
2. add or update a failing test that describes the new contract;
3. edit the owning `data/src/*.json` source and, for a new top-level key, update `data/src/manifest.json`;
4. update the relevant versioned schema and, when necessary, the cross-record validator;
5. run `python tools/build_system_data.py`;
6. run build freshness, Schema and full regression tests;
7. document any semantic change;
8. submit through PR review.

If the change alters semantics rather than merely extending V14.8-compatible data, consider a new schema version instead of silently broadening V14.8.

## Relationship to Issue #4 data splitting

Issue #3 and Issue #4 protect different failure classes:

```text
data/src/*.json
   ↓
Issue #4: ownership + deterministic build + stale-bundle check
   ↓
data/system-data.js / window.V14_DATA
   ↓
Issue #3: JSON Schema + cross-record invariants
   ↓
runtime tests / Pages
```

Issue #4 does not replace Schema validation, and Schema validation does not prove that the generated runtime bundle is synchronized with its source fragments.

The browser runtime remains unchanged: `index.html` still loads `data/system-data.js` synchronously, so the split is a maintenance/build-time concern rather than a new runtime loader architecture.

## Review rule

Schema changes are production contract changes. They require tests and PR review even when no visible UI changes occur, because widening or weakening a schema can silently admit invalid programming data.
