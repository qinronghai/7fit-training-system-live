# 7Fit UX Operating Principles

这份文档把“让用户顺手、出错后能继续、遇到问题能找到人”固化为 7Fit 的产品设计和验收约定。

## 一、产品体验目标

### 1. 正常路径：让用户看得懂、走得通

- 每个页面和模块只突出一个主要下一步。
- 优先让布局、层级和默认值表达含义，避免用额外说明解释本来可以看懂的界面。
- 用户始终能判断：我现在在哪、当前状态是什么、下一步能做什么。
- 高频操作优先使用识别和选择，不要求用户记忆系统规则或内部字段。
- 桌面端和窄屏端保持同一任务顺序；移动端可以改变布局，但不改变用户心智模型。

### 2. 异常路径：让用户知道发生了什么，并能恢复

所有面向用户的异常信息都应尽量包含以下三层：

1. 发生了什么；
2. 已经造成或没有造成什么影响；
3. 用户现在可以采取什么动作。

优先保留用户已经填写、选择或编排的内容。错误状态至少提供一个明确的恢复动作，例如“重试”“重新打开”“返回上一步”或“复制问题信息”。

推荐文案：

> 保存没有收到结果，刚才填写的内容还在。可以重试；如果仍然失败，复制问题信息发给我们。

避免只显示以下类型的技术状态：

- “保存失败”
- “请求错误”
- “Internal error”
- 只有错误码，没有下一步

### 3. 求助路径：让用户在问题现场找到反馈入口

- 全局保持一个稳定、易发现的“反馈”入口，不依赖用户先找到帮助文档。
- 异常状态提供上下文相关的反馈动作，自动带上当前页面、操作和时间。
- 反馈提交后必须明确显示“是否已提交”以及下一步会发生什么。
- 在实际渠道接入前，不伪装成已送达；可以先生成并复制结构化问题信息。
- 联系方式、反馈地址或工单服务统一从配置注入，不散落在页面代码中。

## 二、统一异常状态模型

页面或组件出现异常时，按下面的结构组织内容：

```text
状态标题：用户能理解的结果
影响说明：哪些内容被保留，哪些内容没有发生
恢复动作：当前最可能有效的下一步
备用动作：重试无效时如何反馈或离开
```

例如会员训练记录读取失败：

```text
训练记录暂时无法读取
不会修改已有记录。
[重试]  [反馈问题]
```

## 三、设计评审前的五个问题

每个新页面、流程或重要改动都要回答：

1. 用户进入后，第一眼知道主要任务是什么吗？
2. 正常路径是否可以靠界面本身理解，而不是依赖说明文字？
3. 用户出错时，已经输入或选择的内容是否被保留？
4. 异常信息是否解释了影响，并给出了可执行的下一步？
5. 用户是否能在最需要帮助的地方快速反馈？

如果第 3 或第 4 项无法回答，不能把该状态视为完成；如果第 5 项还没有真实渠道，必须明确标注为“反馈入口已准备，发送渠道待接入”。

## 四、实现边界

- 业务数据、训练语义和内部审计字段不因 UX 文案优化而改变。
- 不为了“解释清楚”添加重复的副标题、提示块或装饰性标签；先检查布局和信息层级是否已经足够表达。
- 技术错误码只用于日志、诊断和结构化反馈，不直接作为用户文案。
- 重试动作必须与实际可恢复性匹配；无法通过重试解决的问题，不应只给“重试”。
- 所有新增的全局帮助或反馈组件都要覆盖桌面、移动端、键盘焦点和窄屏布局。

## 五、交付验收

完成一个功能前，至少提供以下证据：

- 正常路径：主要任务和下一步可见；
- 空状态：用户知道为什么为空以及下一步；
- 加载状态：用户知道系统正在处理；
- 异常状态：有影响说明和恢复动作；
- 反馈路径：入口可见，发送状态诚实；
- 窄屏检查：主要内容和操作没有被截断或挤出视口；
- 浏览器检查：确认实际渲染状态，而不是只确认源代码存在。

这套原则是 7Fit 后续页面、会员中心、编课流程和新产品的共同 UX 基线。
