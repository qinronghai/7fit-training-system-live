# V14.8 Data Sources

## Status

Issue #4 changes the maintenance source of `window.V14_DATA` without changing the browser runtime contract.

The browser still loads:

```html
<script src="data/system-data.js"></script>
```

and application code still reads:

```js
window.V14_DATA
```

The difference is that `data/system-data.js` is now **generated**. Human-maintained source data lives under `data/src/`.

## Source of truth

After Issue #4:

```text
data/src/*.json          ← edit these
        ↓
tools/build_system_data.py
        ↓
data/system-data.js      ← generated; do not hand-edit
        ↓
V14.8 Schema + runtime tests
        ↓
GitHub Pages
```

Normal data work must never start by editing `data/system-data.js` directly.

## Ownership manifest

`manifest.json` is part of the data contract, not documentation-only metadata.

It contains:

```json
{
  "formatVersion": 1,
  "sourceFiles": ["actions.json", "patterns.json", "sessions.json"],
  "owners": {"actions": "actions.json"},
  "topLevelOrder": ["actions"],
  "baselinePayloadSha256": "..."
}
```

### `sourceFiles`

Defines the formal domain file set and deterministic validation order.

### `owners`

Every `window.V14_DATA` top-level key must have exactly one owner.

The builder rejects:

- an undeclared top-level key;
- a key physically present in two fragments;
- a manifest key missing from all fragments;
- a key stored in a file different from its declared owner;
- a source file outside the formal source-file contract.

There is no last-write-wins behavior.

### `topLevelOrder`

Preserves the formal runtime object's original top-level enumeration order independently of domain file order.

This is why splitting the source files does not reorder the generated runtime object.

### `baselinePayloadSha256`

This value is migration provenance for Issue #4.

Baseline:

```text
3bf3874f9e7520c2220b4472e68a51b350b7856460f0987f04f47001c0342358
```

The one-time migration proved that the split-source payload had this same semantic hash before replacing the maintenance source.

**Important:** this hash is not a permanent content freeze. Future approved training-data changes are allowed to change the current payload. Continuous CI does not require current data to equal the Issue #4 baseline hash; it requires source/bundle synchronization and the current V14.8 Schema/invariants.

## Build commands

After editing a source file:

```bash
python tools/build_system_data.py
```

This regenerates:

```text
data/system-data.js
```

Then verify:

```bash
python tools/build_system_data.py --check
python tools/validate_v148_schema.py
python -m pytest -q
for f in tests/*_test.js; do node "$f"; done
find data js -type f -name '*.js' -print0 | xargs -0 -n1 node --check
```

`--check` never rewrites files. It exits non-zero when the committed runtime bundle does not equal the deterministic output from `data/src/`.

## Adding a new field inside an existing top-level object

Example: add metadata inside one Action.

1. Edit `data/src/actions.json`.
2. Do not edit `manifest.json` because the top-level owner remains `actions.json`.
3. Run `python tools/build_system_data.py`.
4. Run the full validation commands.
5. Commit both the source change and regenerated `data/system-data.js`.

## Adding a new top-level key

A new `V14_DATA` top-level key is an architecture change and must be explicit.

1. Decide its business domain.
2. Add the key to exactly one domain JSON file.
3. Add `owners[newKey] = "domain.json"` in `manifest.json`.
4. Insert `newKey` at the intended position in `topLevelOrder`.
5. Run the builder.
6. Extend Schema/validator coverage if the new contract requires it.
7. Run all tests.

If the key has no clear domain owner, stop and resolve the domain model instead of placing it in `system.json` by default.

## Moving a top-level key to another domain file

A move must be atomic:

1. Remove the full key/value from the old JSON fragment.
2. Add it unchanged to the new JSON fragment.
3. Change its `owners` entry.
4. Keep `topLevelOrder` unchanged unless runtime ordering intentionally changes.
5. Build and verify.

The builder rejects half-completed moves.

## Generated file rule

`data/system-data.js` is committed because 7Fit remains a dependency-free static site and GitHub Pages should not need a server-side build phase.

Its committed presence is an output/release convenience, not authority.

If a PR changes only `data/system-data.js`, `build_system_data.py --check` will fail.

If a PR changes only `data/src/*.json` and forgets to regenerate the bundle, the same check will fail.

## CI order

Both feature/PR validation and master Pages release use this order:

```text
pytest
→ build_system_data.py --check
→ validate_v148_schema.py
→ Node runtime tests
→ JS syntax
→ Pages artifact/deploy (master only)
```

Responsibilities remain separate:

- **Issue #3 Schema Gate:** Is the runtime data structurally and semantically legal?
- **Issue #4 Build Gate:** Is the runtime bundle exactly generated from the declared source domains?

Passing one does not replace the other.

## Rollback

If a future source edit causes an incident:

1. Revert the source-data commit and its generated `data/system-data.js` change together.
2. Run `python tools/build_system_data.py --check`.
3. Run Schema and runtime tests.
4. Redeploy from the reverted `master` commit.

Do not repair an incident by manually patching only the generated bundle; that creates source/runtime drift and will be rejected by CI.
