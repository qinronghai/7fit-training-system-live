# Issue #5｜D1 / D2 与 `FLEX_1F_2F` Route 审计

审计基线：`master` `9e428d4`
Issue：[\#5 审计 D1/D2 对 FLEX_1F_2F route 的兼容规则](https://github.com/qinronghai/7fit-training-system-live/issues/5)

## 结论

维持 `D1 / D2 = 1F_ONLY`，不允许仅因为主项允许 `FLEX_1F_2F` 就扩大辅助候选。

这不是对全局 `FLEX` 的否定：

- 正式主项 A / B 继续允许 `1F_ONLY` 与 `FLEX_1F_2F`；因此 L1 徒手深蹲、臀桥仍可进入 Composer。
- D1 / D2 是 Strength 主项的辅助槽，当前职责是补足 A / B 的次级肌群、肩胛与手臂需求。
- D1 / D2 现有辅助池全部对应 1F 力量区动作：腿屈伸、腿弯举、髋内收/外展、臀部后踢、面拉、二头/三头、肩袖等。
- `FLEX_1F_2F` 当前动作均为 2F 热身/激活、SUPPORT 或 CORE 节点；没有证据表明它们应作为 D1 / D2 的 Strength 辅助候选。

## 数据审计

从 `data/system-data.js` 的运行时数据统计：

| Route | 数量 | 当前用途 |
| --- | ---: | --- |
| `FLEX_1F_2F` | 47 | 2F 热身/激活 7 个；SUPPORT 30 个；CORE 10 个 |
| `1F_ONLY` | 118 | 1F Strength 主项及 D1 / D2 辅助池 |

`FLEX_1F_2F` 进入正式主项配置的动作是 `tushen_shendun`（下肢推，L1）和 `tunqiao`（臀伸，L1）；D1 / D2 的 `composer.auxiliaryRules` 引用的动作全部是 `1F_ONLY`。

## 显式规则

`js/composer.js` 现在以命名策略 `AUXILIARY_ROUTE_POLICY` 固化规则：

```js
const AUXILIARY_ROUTE_POLICY = Object.freeze(['1F_ONLY']);
```

`auxCandidates()` 通过 `isAuxiliaryRouteAllowed()` 过滤，而不是依赖散落的 route 字符串比较。这个策略只作用于 D1 / D2，不改变 `byTier()` 对正式主项的 `1F_ONLY + FLEX_1F_2F` 兼容规则。

## 测试覆盖

`tests/composer_runtime_test.js` 覆盖：

- `1F_ONLY` 对 D1 / D2 为正向允许案例；
- `FLEX_1F_2F` 对 D1 / D2 为反向禁止案例；
- 全部 D1 / D2 配置池中的动作均满足显式策略；
- 原有 20 个自由组合 × L1–L4 = 80 个状态仍生成 A / B / C / D1 / D2 / CORE 六槽；
- L1 `FLEX` 徒手深蹲与臀桥仍作为正式主项候选。

本次不改变 `2F PREP → 1F Strength → 2F Recovery` 总动线，不修改既有课程数据，不迁移 route。
